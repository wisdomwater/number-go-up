# Chapter 4

## You Get What You Measure

### Of Course We Want Behavior to Change

At this point, it would be easy to conclude that the safest metric is one nobody knows about.

Measure quietly. Hide the dashboard. Whatever you do, don't let the employees see it.

That would solve one problem by creating several others.

We measure things partly because we want behavior to change.

Suppose a software organization takes twenty-three days, on average, to move a completed change into production. That seems slow. So the team looks at the process, discovers several unnecessary handoffs, and removes them.

Now it takes nineteen days.

They make another improvement.

Fourteen days.

This is measurement doing exactly what we want it to do. Without the number, the organization might have a vague sense that releases are getting faster.

Velocity: feels faster.

With measurement, we have feedback. We can change something, observe what happens, learn from the result, and adjust again.

That feedback loop is one of the great strengths of measurement. It's how athletes improve performance, businesses improve processes, scientists test ideas, and engineers make systems faster and more reliable.

The fact that measurement changes behavior isn't the problem.

Often, changing behavior is the entire point.

The question is **which behavior it changes**.

Consider code review.

Software engineers frequently ask other engineers to review their code before it becomes part of the product. A good reviewer may find a bug, notice a security problem, suggest a simpler design, or ask a question that exposes an assumption the author hadn't considered.

Thoughtful code review can improve software.

Suppose an organization notices that teams using code review consistently have fewer defects.

That's useful information.

So management encourages more code review.

Defects decline.

Wonderful.

We've found a behavior correlated with an outcome we care about, encouraged the behavior, and watched the outcome improve.

This is exactly how metrics are supposed to work.

Then someone asks for a dashboard.

### The Correlation Was Real

The request for a dashboard isn't unreasonable.

If code review is helping, management wants to know whether it's happening consistently. Maybe some teams have adopted the practice while others haven't. Maybe review rates are falling under schedule pressure.

So we begin measuring code-review compliance.

Perhaps 40 percent of changes are reviewed.

We encourage teams to improve.

Now it's 65 percent.

Quality improves.

Excellent.

We keep going.

Eighty percent.

Ninety percent.

Eventually the organization establishes a target:

> Code review compliance must remain above 95 percent.

Notice how the question has changed.

Originally, we were asking:

*Did this change receive a meaningful review?*

Now the system is increasingly asking:

*Did this change receive a review that counts?*

Those questions overlap.

They are not identical.

A careful thirty-minute discussion between two engineers might be enormously valuable but fail to satisfy whatever mechanism records an official review. Meanwhile, a two-second approval in the correct tool may count beautifully.

The original correlation wasn't fake.

That's important.

Code review really may have improved quality. Management didn't invent an arbitrary number and force everyone to worship it. The metric emerged from something that worked.

This is how many problematic metrics begin.

They begin by being useful.

A behavior correlates with an outcome. We encourage the behavior. The outcome improves. The metric appears to confirm that we've found a lever.

So naturally, we pull harder.

This works particularly well at first.

Moving code review from 40 percent to 70 percent may capture a great deal of obvious value. Changes that previously received no second set of eyes now get meaningful scrutiny.

Moving from 70 to 85 percent may still help.

But eventually the easy, valuable opportunities have mostly been captured.

The target keeps going.

At that point, the organization has two ways to produce further improvement.

It can do the difficult work of finding additional ways to improve the underlying reality.

Or it can discover cheaper ways to improve the proxy.

Human beings are quite good at discovering the cheaper route.

This doesn't require dishonesty. It requires optimization.

We do the same thing with project estimates.

Organizations want predictable delivery. That's reasonable. Customers make plans. Other teams have dependencies. Managers need to know when things will arrive.

So teams estimate their work.

Then we compare estimates with actual delivery.

Also reasonable.

Then missed commitments turn red.

Red numbers get discussed.

Teams that consistently hit commitments look good.

Eventually something predictable happens.

Estimates become more conservative.

Management looks at the estimates and asks:

"Why is everyone sandbagging?"

Well.

We asked for predictability.

We measured predictability.

We rewarded predictability.

And people became more predictable.

The metric worked.

Just perhaps not entirely in the way we intended.

This is the central challenge of optimization. A proxy can be genuinely connected to something we care about and still become less useful as we push harder on it.

Our ability to optimize the proxy can eventually outrun the proxy's ability to represent the outcome.

The shortest path to a better number no longer necessarily passes through the thing we were originally trying to improve.

And organizations are built to find short paths.

### Local Optimization, Global Absurdity

The problem gets even more interesting when different parts of an organization optimize different things.

Imagine a software company.

Development wants to deliver features quickly.

Quality wants fewer defects.

Security wants less risk.

Operations wants stability.

Finance wants lower cost.

Management wants predictability.

None of these goals is stupid.

In fact, I'd be concerned about a company that didn't care about them.

So each group builds processes and measurements around the things it is responsible for.

Security notices that some releases contain vulnerabilities.

A new security review is added before release.

Security risk goes down.

Good.

Unfortunately, releases now take longer.

Development adapts.

Instead of sending many small changes through security review, teams begin bundling changes together so they can go through the approval process less often.

Development's efficiency improves.

Unfortunately, larger releases are harder to test and riskier to deploy.

Operations notices.

Operations adds additional pre-release testing.

Stability improves.

Good.

Release time gets longer.

Management notices that projects are becoming harder to predict.

So management adds checkpoints.

Teams now provide more frequent status updates, planning reviews, and milestone reports.

Predictability improves.

Engineers spend more time in meetings.

Productivity declines.

Someone schedules a meeting to discuss why productivity is declining.

Attendance is mandatory.

Nobody had to behave irrationally for us to get here.

Security did its job.

Operations did its job.

Development adapted to the environment.

Management responded to declining predictability.

Every group can point to a legitimate concern, and some may even be able to point to a dashboard demonstrating improvement.

Security incidents are down.

Operational failures are down.

Planning compliance is up.

And the overall system may become miserable.

This is local optimization.

Each part of the organization improves the thing visible from where it stands, while the combined effect makes the larger system worse.

Software engineers encounter this problem constantly in technical systems. You can make one component faster while slowing down the application as a whole. You can reduce memory usage in one place by creating more work somewhere else.

The component metric improves.

The product does not.

Organizations behave the same way.

The difference is that organizational components have meetings.

And incentives.

And vice presidents.

Suppose a senior executive tells the organization that delivery speed needs to improve.

Again, reasonable.

The division leader asks directors what they are doing to improve speed.

Directors ask managers.

Managers look for things their teams can change.

Eventually an engineer gets asked why a bug took nine days to close.

Nobody in that chain needs to be malicious.

The executive is trying to improve competitiveness.

The director is trying to respond to an organizational priority.

The manager is trying to improve team performance.

The engineer is trying to solve a difficult bug.

Each person is acting reasonably from where they stand.

But the pressure changes as it travels.

"Improve delivery speed" becomes "reduce cycle time."

"Reduce cycle time" becomes "why is this number red?"

And the engineer learns something about the environment.

Close bugs faster.

Next time two bugs are waiting—one easy and one difficult—the easy one suddenly has an advantage.

We saw this kind of adaptation in Chapter 2. What's different here is that the employee isn't the only one adapting.

Everyone is.

Managers adapt to the measures above them. Departments adapt to the goals assigned to them. Functions optimize their own responsibilities. The organization becomes a network of locally rational responses.

Then we look at the result and wonder why the system behaves strangely.

A useful question in these situations is:

**What behavior have we made rational?**

That question is more interesting than immediately asking why people are gaming the system.

If an entire sales organization delays deals until the next quarter, something may be wrong with the incentive structure.

If engineers systematically avoid difficult bugs, perhaps the way we reward closure time deserves attention.

If managers keep adding schedule padding, perhaps we've made missing a commitment more dangerous than making an accurate estimate.

Behavior is information too.

This doesn't mean people are never responsible for bad choices.

Sometimes an engineer avoids difficult work because they don't want to do it.

Sometimes a manager pads a schedule because they want an easy target.

Sometimes someone manipulates a metric deliberately.

People remain accountable for their behavior.

But when the same behavior appears repeatedly across many otherwise capable people, it is worth examining the environment before concluding that the organization has mysteriously hired an entire population of bad actors.

The system may be teaching people how to survive inside it.

And sometimes the behavior we want is precisely the behavior that makes the metric look worse.

### Sometimes the Metric Needs to Lose

Return to the customer-service example from Chapter 2.

The organization wants calls resolved efficiently. Eight minutes is the target.

One day a representative receives a complicated call.

The customer has a real problem. Solving it requires looking through several systems, explaining what happened, correcting an error, and making sure the customer understands what to do next.

Thirty-seven minutes later, the problem is solved.

The customer is happy.

The call-duration metric is not.

What should happen?

Someone should probably ask why the call took thirty-seven minutes.

That's what the metric is for.

Maybe the representative needs more training.

Maybe the internal tools are terrible.

Maybe the customer had to repeat information that should already have been available.

Maybe twenty of those thirty-seven minutes were unnecessary.

Or maybe the answer is simply:

This customer needed thirty-seven minutes of help.

In that case, the metric needs to lose.

That's a surprisingly important test of a measurement system.

**Can it lose?**

Can an employee make the number worse and still have made the right decision?

Can a team miss a target and still have exercised excellent judgment?

Can a manager look at a red box, understand what happened, and say:

"Yes. That's exactly what I wanted you to do."

If not, the metric is no longer merely informing judgment.

It has replaced judgment.

This does not mean targets are optional suggestions we can ignore whenever they become inconvenient.

That would be a wonderfully comfortable interpretation of this book.

"I know my numbers are terrible, but Michael said reality is complicated."

Nice try.

Sometimes the number is bad because the situation is bad.

Sometimes a thirty-seven-minute call really should have taken eight.

Sometimes a project misses its schedule because the team planned poorly.

Sometimes a bug takes three weeks because nobody treated it with enough urgency.

Accountability still matters.

The difference is that accountability asks:

*What happened?*

A metric acting as a verdict says:

*The number is bad, therefore someone failed.*

Those are not the same process.

**A metric is information, not a moral judgment.**

A red number tells us where reality differed from an expectation.

Now we need to understand why.

That may lead to coaching.

It may lead to process improvement.

It may lead to changing the target.

It may lead to praising someone for making exactly the tradeoff we hoped they would make.

Sometimes healthy systems produce ugly numbers.

Imagine a hospital with a target for reducing patient wait time. A critically ill patient arrives and requires an unusual amount of attention. Other patients wait longer.

The wait-time metric gets worse.

Good.

Not because waiting is good.

Because the larger purpose mattered more.

The target should influence behavior right up until following it would violate the reason the target exists.

Then the target needs to lose.

This is where judgment enters the system.

And judgment is uncomfortable because it makes management harder.

A rule is easy.

Eight minutes.

A target is clean.

95 percent.

A dashboard can be reviewed quickly.

Judgment requires someone to understand context, weigh tradeoffs, and occasionally explain why a bad-looking number was actually the result of a good decision.

That doesn't scale as neatly.

But neither does reality.

The question isn't whether we can eliminate judgment.

The question is whether we acknowledge that we're already using it.

Someone chose the metric.

Someone chose the target.

Someone chose how much authority to give it.

Those are judgments too.

The only difference is that once they're embedded in a dashboard, they can begin looking like facts.

### Optimize for the Point

Suppose a software team has committed to releasing a product on Friday.

On Wednesday, the team discovers a serious architectural problem.

They have a choice.

Ship Friday and accept the risk.

Or delay the release and fix the problem properly.

The schedule knows one thing.

Friday.

It does not know how serious the architectural problem is. It does not know what failure would cost customers. It does not know whether the team is being appropriately cautious or unnecessarily perfectionistic.

The schedule contains information.

Judgment has to decide what to do with it.

This is why, when a metric begins creating strange behavior, it helps to walk backward.

Suppose we're measuring test coverage.

Why?

Because we want engineers to test the software.

Why?

Because testing helps us find problems.

Why do we care about finding problems?

Because we want reliable software.

Why do we want reliable software?

Because people depend on what we're building.

There.

That's the point.

Now walk forward again.

Does this particular test help us build more reliable software?

If yes, write it.

If we're writing a meaningless test solely to move coverage from 94.8 percent to 95 percent, perhaps the number can lose.

The purpose stays.

The proxy is negotiable.

This sounds simple, but optimization has a way of reversing the order.

We begin with something that matters.

We find something measurable that appears to help.

We improve the number.

The outcome improves.

So we push harder.

Eventually the act of making the number better becomes its own objective, and the original purpose fades into the background.

This is how a company can sincerely value quality while creating a system that rewards shipping too quickly.

It's how a customer-service organization can sincerely value customers while creating pressure to end calls.

It's how a software organization can sincerely value thoughtful engineering while making difficult bugs dangerous to pick up.

Nobody has to stop caring about the point.

They only have to become more accountable for the proxy than for the thing the proxy represents.

The way back is not to stop optimizing.

Optimization is useful.

The way back is to keep the path connected.

The shortest path to a better number should still pass through the outcome we actually care about.

If it doesn't, we need to change the metric, change the incentive, add context, or simply allow judgment to overrule the number.

This requires something from both sides.

Managers have to create room for a person to say, "I know this number looks bad, but here's what happened," without making that sentence sound like the opening statement at a trial.

Employees have to be willing to explain the bad number honestly and accept the possibility that the explanation may not be good enough.

Context is not immunity from accountability.

Measurement is not immunity from judgment.

The point is to put them in conversation.

When a metric and reality disagree, don't automatically discard the metric.

Don't automatically discard the experience either.

Investigate.

Maybe the number sees something we don't.

Maybe the person closest to the work sees something the number cannot.

Maybe both are telling us part of the truth.

Then make a judgment about the thing we actually care about.

That's what the metric was supposed to help us do in the first place.

Companies don't ship dashboards.

They ship products.

Hospitals don't produce wait-time statistics.

They care for patients.

Customer-service organizations don't exist to produce efficient calls.

They help customers.

The number matters because something else matters first.

So measure it.

Track it.

Set targets when targets help.

Use the numbers to challenge stories we'd prefer to tell ourselves.

Hold people accountable when accountability is needed.

But every once in a while, let the metric lose.

The number gets a seat at the table.

It just doesn't get the final word.

**Reality does.**
